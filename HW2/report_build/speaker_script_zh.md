## 投影片 2 — 題目、資料、評分(約 2:00|累計 3:10)

先看**題目**〔指右邊卡片〕:對每位測試使用者,輸出六個 0 或 1,代表——開 pull request、開 issue、在 issue 或 PR 底下留言、送出 PR review、在程式碼行上留 review comment、以及 push commit。這六種就是預測目標。

**資料**方面,是 GH Archive 的每小時事件,官方腳本轉成 8 張匿名化、用外鍵連起來的表。〔可略〕要特別說明,這裡用的是一個**降採樣的鏡像**,一小時只有幾千筆事件,所以我們鎖定的這群使用者其實相當**稀疏**——這點後面會解釋為什麼影響很大。

這份作業的核心難點,其實就是題目要我們回答的兩件事:**跨資料表的關聯**,還有**時間**。這也是後面四個問題的主軸。

## 投影片 5 — Q1:怎麼讀懂這 8 張表(約 1:50|累計 7:40)

在進到模型前,我用一頁幫大家「讀懂」這些表怎麼關聯,這也是第二題的基礎。

**第一,有兩個樞紐實體:**Users 跟 Repositories。幾乎每張表都會用 `author_id` 或 `user_id` 指向某個使用者,再用 `repo_id` 指向某個倉庫。

**第二,有六張事件表:**PullRequests、Issues、IssueComments、PRReviews、PRReviewComments、Pushes。它們每一列就代表一次行為——**某個人、在某個 repo、在某個時間**。

**第三,外鍵會串成鏈。**〔可略〕舉例來說,一則 review 會指向它所屬的 PR;一則程式碼行的 review comment 又同時指向那個 PR 跟那則 review;一則 issue 留言指向它所屬的 issue。而且這些留言跟 review 本身也都帶著 `repo_id`。

**為什麼這很重要?**因為沿著 `repo_id`,我可以找到**同一個 repo 裡的其他協作者**;沿著 `author_id`,我可以找到**一個人在別的地方的歷史**。這正是我第二題的關聯特徵在利用的結構。〔指右表〕右邊這張對照表,列出六個要預測的活動分別來自哪張表、哪個欄位代表「做這件事的人」,例如 pr_review 是看 PRReviews 的 reviewer_id。

## 投影片 7 — Q2:如何跨資料表建模(約 2:10|累計 10:10)

**第一,外鍵 join 特徵。**我把 User、PR、Review、Issue、Comment 串起來,算出一些跨表的統計量,例如:你的工作收到多少 review 跟留言、有多少**不同的人**來 review 你或跟你合作、你自己又送出多少 review,以及你參與的 repo 和組織的廣度。〔可略〕這些都是「你跟別人的互動」,單看一張表是看不到的,一定要 join 才算得出來。

**第二,repo 鄰域聚合。**對於一個使用者碰過的 repo,我把這些 repo 最近的活動量、還有有多少其他活躍使用者,聚合起來,代表這個人所在社群的「**動能**」。〔可略〕直覺是:一個待在很熱門、很活躍 repo 的人,下週繼續活動的機率,通常比待在冷清 repo 的人高。

**第三,時間感知的異質圖神經網路**,概念上就是課堂上提到的 RelBench、關聯式深度學習那一套。我建了一個使用者對 repo 的圖,有 6 種從外鍵衍生出來的邊,讓訊息從使用者傳到 repo、再傳回兩跳之外的協作者,也就是「跟我用同一個 repo 的人」。

前兩個是整理成特徵餵給樹模型,第三個是端到端的圖神經網路。下一頁我就直接看,這些關聯到底有沒有幫助。

---

## 投影片 8 — Q2:關聯特徵的實際貢獻(約 2:10|累計 12:20)

這裡我要**誠實**報告結果:在這個稀疏的使用者群上,關聯結構幫助很小。

〔指三張卡片〕第一,GBDT 把關聯特徵整組拿掉,Score 從 33.1 變 33.6,**幾乎沒差**,甚至還微幅上升。第二,給 GNN 加上圖的訊息傳遞,反而**掉了約 8.5 分**,從只用節點特徵的 30.3 掉到 21.8。第三,所以綜合起來,**最好的模型還是 GBDT**,用時間加關聯特徵。

**為什麼會這樣?**〔可略〕這其實是一個蠻有意思的結果。原因是:下一週的活動,主要是由使用者**自己最近的行為**決定的,也就是很強的時間自相關;而這個使用者對 repo 的圖又很稀疏,平均式的聚合會把訊號「**抹平**」,反而讓 GNN 失去了每個人的個別特徵。

關聯式深度學習通常是在**跨實體互動很密集**的時候才會發揮威力;而在這個題目上,是時間在主導。這本身就是一個有價值的發現——它告訴我們 RDL 什麼時候才划算。〔可略〕我也用每個活動的 AUC 驗證過,一旦加上訊息傳遞,AUC 大概就掉到 0.5 左右,也就是接近亂猜,這跟上面的分數是一致的。

## 投影片 10 — Q3:如何建模時間資訊(約 2:30|累計 15:10)

一樣三個重點。

**第一,多尺度的時間特徵。**我對每一種活動,分別算 1、7、14、30、90 天這幾個窗口的次數。〔可略〕用多個窗口的用意是:短窗口抓「最近的爆發」,長窗口抓「長期的習慣」,兩種訊號都保留。除了次數,我還算距離上次活動多久、也就是 recency、有幾天是活躍的、以及 7 天的動能跟比率。其中有一個特別強的訊號,就是**直接參考上一週有沒有做**——因為「上週做過、這週通常也會做」。

**第二,嚴格的防洩漏控制。**只有 row-time 小於 t 的資料列看得到;我**絕對不用** `created_at` 或 `submitted_at` 來判斷可見性,因為那些列其實是**晚點才進到資料裡**的,用它們就等於偷看未來;我也**絕對不用**那些只有事後才知道的欄位,像 `merged_at`、`closed_at`、`state_reason`、`dismissed_at`。

**第三,把時間編碼進 GNN 的邊。**每一條邊都帶著它的「**年齡**」,鄰居傳過來的訊息會用 **exp(負的 age 除以 τ)** 來加權,讓最近的互動比舊的更重要。

〔指下面時間軸〕這條時間軸就是我切分的方式:**t 之前的所有歷史**拿來當特徵,**接下來 7 天**拿來當標籤。

## 投影片 11 — Q3:時間訊號最關鍵(約 1:50|累計 17:00)

這頁用兩張圖,量化地說明時間建模的效果。

〔指左圖〕左邊是**特徵群的消融實驗**,也就是一次拿掉一整組特徵,看分數掉多少。可以很明顯看到,把**時間特徵拿掉,Score 從 33.1 掉到 29.0,掉了 4.1 分**,是所有特徵群裡面掉最多的。〔可略〕對照一下,光是「照抄上一週」這個最簡單的基準就有 29.3 分,可見時間資訊幾乎撐起了整個分數。

〔指右圖〕右邊是 GBDT 在各個活動上的 F1。可以看到**規律型的行為**,像開 issue、送 PR review,比較好預測;而**爆發型的行為**,像 push、程式碼行的 review comment,就比較難,因為它們比較零星、不規律,不容易從歷史外推。

所以這頁直接回答了「時間建模帶來什麼幫助」:它是這個任務裡**最主要的訊號來源**。

## 投影片 14 — Q4:完整流程逐步說明(約 1:50|累計 20:50)

整個流程分成六步。

**第一,前處理。**下載 GH Archive 的每小時檔,跑官方 `preprocess.py`,得到 8 張匿名化的表,每張一個 Parquet 檔。

**第二,建立樣本。**組成「使用者加上一個時間切點」的資料列,標籤就是這個人在接下來 7 天有沒有做各個活動;而且只有 row-time 小於切點的資料看得到。〔可略〕我用好幾個過去的週各做一份,堆疊起來當訓練資料,這樣樣本數才夠。

**第三,特徵表示。**時間特徵、關聯特徵,再加上時間感知的使用者對 repo 圖。

**第四,建模。**每個活動各訓練一個 LightGBM,總共 6 個;另外還有一個異質 GNN 做對照;每個活動的**判斷門檻**都在驗證週上調到讓 F1 最大。

**第五,驗證與預測。**依時間切分,用較早的週訓練、留一週驗證;確認方法後,用全部資料重新訓練,再預測測試週,輸出 `output_413551034.csv`。

**第六,可重現性。**套件版本鎖定、亂數種子固定、資料區間記錄清楚,所以助教只要重跑 `preprocess.py`,就能重現我的輸出。

## 投影片 15 — 訓練設定:依時間切分(約 2:10|累計 23:00)

這頁把「到底怎麼訓練」再講清楚。

〔指上排〕上面這一排是我的**週切點**:用 10 月 13、20、27 這三個比較早的週當訓練,留下 11 月 3 到 10 號這一週當驗證。〔指三張卡片〕底下三張卡片是三個重點。

**第一,依時間切、不隨機切。**早的週拿來訓練,晚的一週拿來驗證,這正好模擬「用過去預測未來」,也避免洩漏。〔可略〕如果像一般機器學習那樣隨機亂切,就會把未來的資料混進訓練,驗證分數會虛高,上線後卻一落千丈。

**第二,六個 LightGBM。**每個活動各訓練一個梯度提升樹模型,彼此獨立。〔可略〕分開訓練的好處是,每個活動可以各自學到自己的規律,不會互相干擾。參數大概是 400 棵樹、學習率 0.03、subsample 0.8、加上 L2 正則;而且**種子固定在 42、開 deterministic**,所以助教重跑可以得到一模一樣的結果。

**第三,每個活動各自調門檻。**模型輸出的是機率,要用一個門檻把它變成 0 或 1。我讓每個活動分別在驗證週上挑「讓 F1 最高」的門檻,因為各個活動的正例比例差很多——像 push 很多,但程式碼行的 review comment 很少,用同一個門檻會吃虧。
